2. Credenciales de AWS Academy (lo que hay que entender)

Tu cuenta es AWS Academy Learner Lab, no una cuenta AWS normal. Eso implica:

  1. No hay facturación: el lab tiene un presupuesto fijo y las credenciales son temporales.
  2. No puedes crear roles IAM. El lab ya trae LabRole y el perfil de instancia LabInstanceProfile. Por eso el stack de CloudFormation usa IamInstanceProfile: LabInstanceProfile en vez de crear uno.
  3. Las credenciales de la consola duran ~4 horas y hay que refrescarlas con el botón AWS Details.
  4. La región es fija: us-east-1.
  5. La key pair es fija: vockey, y el archivo privado es labsuser.pem.

2.1 Por qué se usó CloudFormation y no la CLI directamente

El aws_session_token que llegó por chat estaba truncado (756 caracteres; al decodificar base64 quedaban 567 bytes y la firma se cortaba a la mitad), por lo que aws sts get-caller-identity devolvía InvalidClientTokenId. La solución fue:

  1. Abrir la consola con la URL de federación del lab (ssourl.txt).
  2. Crear la instancia con un stack de CloudFormation (infra/academy/stack-ec2.yaml) desde la consola.
  3. Entrar por SSH con labsuser.pem.
  4. Leer credenciales válidas desde el metadata service (IMDSv2) de la propia instancia, que hereda LabRole:
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/iam/security-credentials/LabRole

Con esas credenciales (ASIAZQ3DQKU2NOHOVYCA, rol LabRole) se pudo usar la CLI para Cognito, API Gateway y las verificaciones. Expiran a las 2026-11-02T07:23:28Z.

Si necesitas repetir el despliegue desde cero: refresca las credenciales en AWS Details, pégalas completas (las tres líneas: access key, secret key y session token entero), y ejecuta los scripts de infra/academy/ en orden.

3.1 Por qué existe frontend-tls

Cognito rechaza callbacks con http:// cuando el host no es localhost:

InvalidParameterException: ... cannot use the HTTP protocol

Por eso el frontend se publica en https://32.200.126.178:8443 con un certificado autofirmado (subjectAltName = IP:32.200.126.178). El navegador mostrará una advertencia de certificado: es esperado, se acepta con "Avanzado → Continuar".

3.2 Límites de memoria (la instancia tiene solo 913 MB de RAM)

backend:
  environment:
    JAVA_TOOL_OPTIONS: "-Xmx256m -XX:MaxMetaspaceSize=160m"
  mem_limit: 460m

Además se agregó 2 GB de swap en la instancia:

sudo dd if=/dev/zero of=/swapfile bs=1M count=2048
sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile

Sin el swap, los dos nodos de RabbitMQ + la JVM hacían que el OOM killer matara contenedores.

4. RabbitMQ — mapeo con la rúbrica

Verificado con rabbitmqctl cluster_status y rabbitmqctl list_queues:

  • Clúster de 2 nodos: rabbit@rabbitmq-1 + rabbit@rabbitmq-2, cluster_name = pedidos360-cluster, disk_nodes = ambos, partitions: {} (sin particiones de red).
  • 3 colas de negocio: notificaciones.queue, tickets.queue, documentos.queue.
  • 3 colas de mensajes muertos: notificaciones.dlq, tickets.dlq, documentos.dlq.
  • Exchanges: pedidos.direct (direct), pedidos.topic (topic), pedidos.dlx (direct, DLX).
  • Política de alta disponibilidad: ha-all con patrón ^(?!amq\.) → {"ha-mode":"all","ha-sync-mode":"automatic"}.
  • Consumidores activos: 1 en cada .queue (3 en total).

4.1 Detalle importante: definitions.json

El archivo infra/rabbitmq/definitions.json se importa al arrancar. Dos cosas que costaron sangre:

  1. "parameters" debe ser una lista ([]), no un objeto ({}). Si es {}, RabbitMQ falla con error:badarg ... erlang:length/1 args: [#{}] y el nodo no arranca.
  2. Al importar definiciones se desactiva la creación del usuario por defecto, así que el usuario pedidos debe venir en el JSON con su hash real:
"users": [{
  "name": "pedidos",
  "password_hash": "7CPBC6No0DVVdJw5LLUmYbq0A+5uH196TaG2HXQDkUPRYsXE",
  "hashing_algorithm": "rabbit_password_hashing_sha256",
  "tags": "administrator"
}]

El hash corresponde a la contraseña pedidos123 y se calcula como base64( salt[4 bytes] || sha256(salt || password) ).

  1. El nodo 2 también necesita el volumen de definitions.json, porque rabbitmq.conf lo referencia y falla con management.load_definitions invalid, file does not exist.

4.2 Demostración de DLQ

Dos bugs que hay que conocer:

  1. Sin {proxy} en la URI de integración, API Gateway reenviaba /api/pedidos como / y el backend respondía 500 "Error interno" (el GlobalExceptionHandler se comía la excepción).
  2. El preflight OPTIONS caía en la ruta JWT y devolvía 401. Se creó una ruta OPTIONS /{proxy+} con --authorization-type NONE, que ahora responde 200 con access-control-allow-origin: *.

5.3 Frontend

frontend/src/authConfig.ts incluye metadata OIDC estática porque el dominio de Cognito devolvía 404 en /.well-known/openid-configuration (problema de propagación de CloudFront):

metadata: ({
  issuer,
  authorization_endpoint: `${authority}/oauth2/authorize`,
  token_endpoint: `${authority}/oauth2/token`,
  userinfo_endpoint: `${authority}/oauth2/userInfo`,
  end_session_endpoint: `${authority}/logout`,
  jwks_uri: `${issuer}/.well-known/jwks.json`,
  ...
} as any)

Con eso el login funciona: botón → Hosted UI → credenciales → vuelta a la app con el JWT en memoria.

8. Operación y limpieza

8.1 Detener la instancia (importante para no agotar el lab)

aws ec2 stop-instances --region us-east-1 --instance-ids i-03a70f0a716b69333

O desde la consola: EC2 → Instances → pedidos360-eval2 → Instance state → Stop instance. Detenerla no borra nada (el disco EBS se conserva), solo deja de consumir el presupuesto de horas.

8.2 La IP es fija (Elastic IP)

La instancia tiene asociada la Elastic IP 32.200.126.178 (eipalloc-04b1dfc182682f987), por lo que detener y volver a arrancar no cambia la IP y no hay que reconfigurar nada.

No liberes esa Elastic IP. Si se libera, el siguiente arranque asignará una IP nueva y habrá que repetir los pasos de §8.2-bis (API Gateway + Cognito + certificado + rebuild del frontend).

8.2-bis Si aun así cambia la IP

NEW_IP=$(aws ec2 describe-instances --region us-east-1 --instance-ids i-03a70f0a716b69333 \
  --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)

# API Gateway
aws apigatewayv2 update-integration --api-id bf0plxi897 --integration-id <ID> \
  --integration-uri "http://$NEW_IP:8080/{proxy}"

# Cognito (callbacks)
aws cognito-idp update-user-pool-client --user-pool-id us-east-1_9b2C1fxtb \
  --client-id 261rvdvemjgib6n86vrb05tl9k \
  --callback-urls "[\"https://$NEW_IP:8443\",\"http://localhost:5173\"]" \
  --logout-urls  "[\"https://$NEW_IP:8443\",\"http://localhost:5173\"]" \
  --allowed-o-auth-flows code --allowed-o-auth-scopes openid email profile \
  --allowed-o-auth-flows-user-pool-client \
  --supported-identity-providers COGNITO \
  --explicit-auth-flows ALLOW_USER_PASSWORD_AUTH ALLOW_REFRESH_TOKEN_AUTH

Además hay que regenerar el certificado autofirmado con el nuevo subjectAltName y reconstruir el contenedor frontend-tls.

Nota: ya está aplicado — la instancia usa Elastic IP, así que este procedimiento solo hace falta si alguien libera la EIP. En AWS Academy una EIP asociada a una instancia corriendo no tiene costo.
